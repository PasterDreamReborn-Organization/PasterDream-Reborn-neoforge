# PasterDream Reborn — NeoForge 1.21.1 移植总纲与骨架方案

> 本文是 Forge 1.20.1 → NeoForge 1.21.1 的搬运总纲：技术选型、框架对照、关键 API 差异、目录映射、骨架搭建阶段与风险清单。
>
> 目标仓库：`PasterDream-Reborn-neoforge`（NeoForge 21.1.249 / MC 1.21.1）
> 源仓库：`PasterDream-Reborn-forge1.20.1`（Forge 47.x / MC 1.20.1）
> 包名 `com.pasterdream.pasterdreammod`，modid `pasterdream` 两边保持一致。

## 二、核心决策

1. **包名 / 类名 / `MOD_ID` 与源仓库保持一致**。
   - 源：`PasterDreamMod.MOD_ID`；目标当前 MDK 示例是 `PasterDreamMod.MODID`。骨架统一改回 `MOD_ID`，减少搬运时的机械改名。
   - 类名沿用 `ModBlocks` / `ModItems` / `PasterDreamMod` 等，便于逐文件对照搬运。
2. **目录结构镜像源仓库**（`init/ world/ worldgen/ client/ datagen/ network/ event/ capability/ command/ recipe/ helper/ component/ compat/ advancement/ mixin/ tag/ config/ util/`）。
3. **基础注册仍用 `DeferredRegister`**，但注册表常量从 `ForgeRegistries.*` 换成 `net.minecraft.core.registries.Registries` / `NeoForgeRegistries`，`RegistryObject` 换成 `DeferredHolder` / `DeferredItem` / `DeferredBlock`。
4. **NBT → DataComponents**：优先为真实状态定义强类型 `DataComponentType`；零散/历史 NBT 用原版 `DataComponents.CUSTOM_DATA`（`CustomData`）过渡。
5. **网络整体重写为新 payload 框架**（`CustomPacketPayload` + `StreamCodec` + `RegisterPayloadHandlersEvent`）。
6. **SAN / 融梦能量**从 Forge Capability 迁移到 NeoForge `AttachmentType`（带 serialize/sync）。
7. **附魔、画**改为数据驱动注册表（`RegistrySetBuilder` + datagen），不再 `DeferredRegister`。

## 三、源项目框架总览

### 3.1 入口

`PasterDreamMod.java:65` 构造方法 `(FMLJavaModLoadingContext context)`：
- `GeckoLib.initialize()`
- `context.getModEventBus()` 注册约 20 个 `DeferredRegister`
- `modEventBus.addListener(commonSetup / clientSetup)`
- `MinecraftForge.EVENT_BUS.register/addListener(...)` 挂运行时事件
- `context.registerConfig(COMMON, Config.SPEC)` + `(CLIENT, PasterDreamClientConfig.SPEC)`

### 3.2 分层职责

| 包 | 职责 | 备注 |
|----|------|------|
| `init/` | 所有注册对象集中管理（38 个 hub 文件） | 不做业务逻辑 |
| `world/` | block / item / entity / effect / fluid / fluidtype / skill / wind / behavior / conditions / dimension / enchantment / functions | 客制化类最小化 |
| `worldgen/` | ConfiguredFeature / PlacedFeature / Biome / Dimension / Structure 的 `ResourceKey` + bootstrap | 由 datagen 产出 JSON |
| `client/` | RenderType、HUD、粒子、音效、模型、渲染器、BOSS 音乐 | `@EventBusSubscriber(value = Dist.CLIENT)` |
| `datagen/` | `ModDataGenerator` + common/lang/util 全部 Provider | 唯一 JSON 来源 |
| `network/` | 28 个数据包，`SimpleChannel.registerMessage(id++, ...)` | 按子功能分子包 |
| `capability/` | MeltDreamEnergy + SAN，`接口 + 实现 + Provider` | Forge Capability |
| `event/` | 运行时事件处理器 | `MinecraftForge.EVENT_BUS` |
| `command/` `recipe/` `helper/` `component/` `compat/` `advancement/` `mixin/` `tag/` `config/` `util/` | 见 `document/rule/program/目录结构组织.md` | — |

### 3.3 资源

- `src/main/resources/assets/pasterdream/`（geo、animations、textures、models、particles、sounds、patchouli_books、lang）
- `src/main/resources/data/pasterdream/`（手动维护的 loot_tables / recipes / san_biome_rates / structures / worldgen / patchouli_books）
- `src/main/resources/data/curios/tags/items/`（饰品槽位标签，手动维护）
- `src/generated/resources/`（datagen 输出，不可手改）

## 四、关键 API 差异清单（骨架层）

### 4.1 入口类与事件总线

| 源 | 目标 |
|----|------|
| `public PasterDreamMod(FMLJavaModLoadingContext context)` | `public PasterDreamMod(IEventBus modEventBus, ModContainer modContainer)` |
| `context.getModEventBus()` | 直接使用注入的 `modEventBus` |
| `context.registerConfig(type, spec)` | `modContainer.registerConfig(type, spec)` |
| `GeckoLib.initialize()` | GeckoLib 4.9.2 自动初始化，通常**不再需要**调用（搬渲染时验证） |
| `@Mod.EventBusSubscriber(bus = Mod.EventBusSubscriber.Bus.MOD)` | `@EventBusSubscriber(modid = MOD_ID)`，`bus` 已废弃并忽略 |

`@EventBusSubscriber` 在 1.21.1 按事件类型自动分流：实现 `IModBusEvent` 的事件进 Mod 总线，其余进 `NeoForge.EVENT_BUS`（已核对 loader 4.0.44 源码）。因此**不要**再写 `bus = ...`。

### 4.2 注册表

```java
// 源（Forge）
public static final DeferredRegister<Item> ITEMS =
        DeferredRegister.create(ForgeRegistries.ITEMS, MOD_ID);
public static final RegistryObject<Item> X = ITEMS.register("x", () -> new Item(...));

// 目标（NeoForge）
public static final DeferredRegister.Items ITEMS = DeferredRegister.createItems(MOD_ID);
public static final DeferredItem<Item> X = ITEMS.register("x", () -> new Item(...));
```

对照表：

| 对象 | 目标 DeferredRegister 工厂 / 注册表 |
|------|--------------------------------------|
| 物品 | `DeferredRegister.createItems(MOD_ID)` → `DeferredItem` |
| 方块 | `DeferredRegister.createBlocks(MOD_ID)` → `DeferredBlock` |
| 方块实体 | `DeferredRegister.create(BuiltInRegistries.BLOCK_ENTITY_TYPE, MOD_ID)` |
| 实体 | `DeferredRegister.create(Registries.ENTITY_TYPE, MOD_ID)` |
| 创造物品栏 | `DeferredRegister.create(Registries.CREATIVE_MODE_TAB, MOD_ID)` |
| 药水效果 | `Registries.MOB_EFFECT` |
| 药水 | `Registries.POTION` |
| 属性 | `Registries.ATTRIBUTE` |
| 粒子类型 | `Registries.PARTICLE_TYPE` |
| 声音事件 | `Registries.SOUND_EVENT` |
| 配方类型 / 序列化器 | `Registries.RECIPE_TYPE` / `Registries.RECIPE_SERIALIZER` |
| 自定义 Feature | `Registries.FEATURE` |
| 树叶放置器 / 树木装饰器 | `Registries.FOLIAGE_PLACER_TYPE` / `Registries.TREE_DECORATOR_TYPE` |
| 流体 | `Registries.FLUID` |
| 流体类型 | `NeoForgeRegistries.FLUID_TYPES` |
| DataComponent | `Registries.DATA_COMPONENT_TYPE` |
| Attachment | `NeoForgeRegistries.Keys.ATTACHMENT_TYPES` |
| 群系修饰符 | `NeoForgeRegistries.Keys.BIOME_MODIFIERS` |

> **附魔 / 画**：1.21 起 `Enchantment`、`PaintingVariant` 是数据驱动注册表，不再走 `DeferredRegister`，见 4.6。

### 4.3 网络

`SimpleChannel` / `registerMessage` 已移除，改为 payload 框架：

```java
// payload 定义
public record BlinkPacket(float yaw) implements CustomPacketPayload {
    public static final CustomPacketPayload.Type<BlinkPacket> TYPE =
            new CustomPacketPayload.Type<>(ResourceLocation.fromNamespaceAndPath(MOD_ID, "blink"));
    public static final StreamCodec<RegistryFriendlyByteBuf, BlinkPacket> STREAM_CODEC =
            StreamCodec.composite(ByteBufCodecs.FLOAT, BlinkPacket::yaw, BlinkPacket::new);

    @Override
    public CustomPacketPayload.Type<? extends CustomPacketPayload> type() {
        return TYPE;
    }

    public void handle(IPayloadContext ctx) {
        ctx.enqueueWork(() -> { /* 主线程逻辑 */ });
    }
}

// 注册（Mod 总线）
@EventBusSubscriber(modid = MOD_ID)
public final class ModNetwork {
    @SubscribeEvent
    public static void register(RegisterPayloadHandlersEvent event) {
        PayloadRegistrar registrar = event.registrar("1");
        registrar.playToServer(BlinkPacket.TYPE, BlinkPacket.STREAM_CODEC, BlinkPacket::handle);
        registrar.playToClient(SanSyncPacket.TYPE, SanSyncPacket.STREAM_CODEC, SanSyncPacket::handle);
        // 双向：registrar.playBidirectional(...) / commonBidirectional(...)
    }
}

// 发送
PacketDistributor.sendToServer(payload);
PacketDistributor.sendToPlayer(serverPlayer, payload);
PacketDistributor.sendToAllPlayers(payload);
```

### 4.4 NBT → DataComponents（最大改动）

`ItemStack.getOrCreateTag()` / `CompoundTag` 存储路线在 1.21 改为数据组件：

- **强类型状态**（等级、类型、内容 key 等）：定义 `DataComponentType`，`DeferredRegister.create(Registries.DATA_COMPONENT_TYPE, MOD_ID)`，用 `Codec` + `StreamCodec`。
- **历史/自由 NBT**：用原版 `DataComponents.CUSTOM_DATA`（`CustomData.get(stack)` / `CustomData.set(...)`）。
- 方块实体、实体仍可用 `saveAdditional`/`loadAdditional` + `CompoundTag`（`BlockEntity`/`Entity` API 未变）。

> 影响面：研钵、笔记、蓝图、预言卡、药剂瓶、存储袋、融梦水晶箱等所有依赖 NBT 的物品/容器。

### 4.5 数据驱动注册表（附魔 / 画）

```java
// 源：DeferredRegister<Enchantment> ENCHANTMENTS = create(ForgeRegistries.ENCHANTMENTS, MOD_ID);
// 目标：改为 ResourceKey + datagen bootstrap
public static final ResourceKey<Enchantment> SHELTER = key("shelter");
// ModWorldGenProvider 的 RegistrySetBuilder 中：
//   builder.add(Registries.ENCHANTMENT, ModEnchantments::bootstrap);
//   builder.add(Registries.PAINTING_VARIANT, ModPaintings::bootstrap);
```

附魔效果改为 `EnchantmentEffectComponents`（如 `EnchantmentEffectComponents.POST_ATTACK`、`DAMAGE_PROTECTION` 等），1.21 的原版机制与 1.20.1 手写 `doPostHurt` 差异大，需逐个重写。

### 4.6 数据生成

| 源 | 目标 |
|----|------|
| `net.minecraftforge.data.event.GatherDataEvent` | `net.neoforged.neoforge.data.event.GatherDataEvent` |
| `net.minecraftforge.common.data.BlockTagsProvider` 等 | `net.neoforged.neoforge.common.data.*` |
| `@Mod.EventBusSubscriber(bus = Bus.MOD)` | `@EventBusSubscriber(modid = MOD_ID)`（`GatherDataEvent` 是 `IModBusEvent`） |
| `DatapackBuiltinEntriesProvider` | 同（neoforge 版本），用于世界生成 / 附魔 / 画 |

### 4.7 群系修饰符

`ForgeRegistries.Keys.BIOME_MODIFIERS` → `NeoForgeRegistries.Keys.BIOME_MODIFIERS`；`BiomeModifier` 的 codec/注册方式与 1.20.1 近似，datagen 标签 `neoforge:add_spawns`（原 `forge:add_spawns`）。

### 4.8 Capability → Attachment

```java
public static final DeferredRegister<AttachmentType<?>> ATTACHMENTS =
        DeferredRegister.create(NeoForgeRegistries.Keys.ATTACHMENT_TYPES, MOD_ID);

public static final DeferredHolder<AttachmentType<?>, AttachmentType<SanData>> SAN =
        ATTACHMENTS.register("san", () -> AttachmentType.builder(SanData::new)
                .serialize(SanData.SERIALIZER)   // IAttachmentSerializer / INBTSerializable
                .sync(SanData.SYNC_HANDLER)      // 可选，自动同步
                .copyOnDeath()
                .build());
```

读写：`player.getData(SAN.get())` / `player.setData(...)`。`SimpleChannel` 手写同步可被 `sync(...)` 替代，视需求保留。

> **注意**：`Entity#getPersistentData()` 在 NeoForge 1.21.1 仍存在（`IEntityExtension`，已核对源码），暗影难度系统的单 int 覆盖方案可原样保留。

### 4.9 流体

- `FluidType` 注册表：`NeoForgeRegistries.FLUID_TYPES`（原 `ForgeRegistries.Keys.FLUID_TYPES`）。
- `ForgeMod.enableMilkFluid()` → NeoForge 对应 API（搬流体时确认）。
- 流体容器 `IFluidHandler`/`FluidUtil` 仍在 `net.neoforged.neoforge.fluids.*`。

### 4.10 第三方

| 依赖 | 主要变化 |
|------|----------|
| GeckoLib 4.9.2 | 包名/接口基本延续 `software.bernie.geckolib`；初始化、方块 `AnimatableInstanceCache`、渲染器注册事件需按 4.9 文档核对 |
| Curios 9.5.1 | 包名 `top.theillusivec4.curios`；`ICurioItem` 方法签名、`CuriosApi` 查询、`InterModComms` 槽位注册有变动 |
| Patchouli 1.21.1-93 | 书籍数据格式/API 版本升级 |
| JEI 19.51 | `@JeiPlugin` + `IRecipeCategory` 基本结构不变，`RecipeType`/`IFocus` 细节有调整 |
| KubeJS 2101 | 插件入口/API 大改 |

## 五、目录映射（源 → 目标）

目标目录与源**同名同结构**，仅换 API。差异点：

```
src/main/templates/META-INF/neoforge.mods.toml   ← 替代 resources/META-INF/mods.toml
src/main/java/com/pasterdream/pasterdreammod/
├── PasterDreamMod.java        MOD_ID、构造注入、注册中枢
├── Config.java                保留，移到 config/ 或留根包（建议留根包对齐源）
├── config/PasterDreamClientConfig.java
├── init/                      Mod* hub（注册 API 全部换成 NeoForge）
├── world/                     block/item/entity/effect/fluid/...（类名不变）
├── worldgen/                  bootstrap（enchantment/painting 也进这里）
├── client/                    ModClientEntry + HUD/model/renderer/particle
├── datagen/                   ModDataGenerator + Provider
├── network/                   payload 重写
├── capability/                接口/实现保留，注册换 AttachmentType
├── event/                     NeoForge.EVENT_BUS + @EventBusSubscriber
├── command/ recipe/ helper/ component/ compat/ advancement/ mixin/ tag/ util/
src/main/resources/
├── assets/pasterdream/        原样拷贝
├── data/pasterdream/          原样拷贝（注意 1.21 目录名变化，见下）
├── data/curios/tags/items/    原样
├── data/minecraft/tags/       painting_variant 目录等按 1.21 调整
```

- 战利品表：`loot_tables/` → `loot_table/`（datagen 路径按 1.21 输出）。
- 配方：`recipes/` → `recipe/`。
- 进度：`advancements/` → `advancement/`。
- 结构集/模板池：`structure_sets/` → `structure_set/`、`template_pools/` → `template_pool/`。
- 画：`painting_variant` 数据驱动。

> 以 `runData` 实际输出为准，不手写这些路径。

## 六、骨架搭建阶段

### Phase 0 — 环境与元数据（已完成）
- 依赖 jar 放入 `libs/`，`build.gradle` flatDir 引用
- `gradle.properties` 技术参数、`neoforge.mods.toml` 依赖声明

### Phase 1 — 基础骨架
1. `PasterDreamMod.java`：改为 `MOD_ID`、构造注入、`ModContainer` 注册 Config，移除 example 内容
2. `Config.java`：对齐源 `Config.java`（COMMON 配置项，含暗影难度/低 SAN 视觉等）——先留空壳分批搬
3. `config/PasterDreamClientConfig.java`：CLIENT 配置
4. `client/PasterDreamClientEntry`（原 `PasterDreamRebornClient`）：`@Mod(dist=CLIENT)` + Config 界面
5. 建立 `init/` 空 hub 类骨架（每个 `DeferredRegister` + `register(IEventBus)`）

### Phase 2 — 数据层骨架
1. `tag/ModBlockTags`、`ModItemTags`、`ModEntityTypeTags` 常量
2. `datagen/ModDataGenerator`：`GatherDataEvent` + 全部 Provider 空壳
3. `datagen/common/*` Provider 骨架（BlockState/BlockLoot/EntityLoot/Tags/ItemModels/Recipes/Advancement/BiomeModifier/WorldGen）
4. `datagen/lang/ModEnUs|ModZhCn`
5. `worldgen/` bootstrap 骨架（ConfiguredFeature / PlacedFeature / Biome / Dimension / Enchantment / Painting）

### Phase 3 — 基础设施
1. `network/` 新 payload 框架 + `ModNetwork`（`RegisterPayloadHandlersEvent`）
2. `capability/` 或 `attachment/`：SAN + 融梦能量 `AttachmentType` 基座
3. `event/` 事件入口（`NeoForge.EVENT_BUS` 注册约定）
4. `command/PasterDreamDebug` 根命令
5. `helper/` 通用工具骨架

### Phase 4 — 资源骨架
1. 建立 `assets/pasterdream/`、`data/pasterdream/`、`data/curios/tags/items/` 目录
2. `pasterdream.mixins.json` 清空重写（`compatibilityLevel = JAVA_21`）
3. `sounds.json`、`particles/`、`geo/`、`animations/` 目录占位

### Phase 5 — 逐系统搬运（按优先级，使用 skills）
建议顺序：注册基础 → 方块/物品/工具/护甲 → 粒子/音效/渲染 → 实体 → 流体/容器配方 → 世界生成 → 能力/SAN/暗影难度 → 技能 → 进度/笔记 → JEI/KubeJS 兼容。

### Phase 6 — 验证
- `./gradlew build`（编译 + 元数据）
- `./gradlew runData`（检查 `src/generated/`）
- `./gradlew runClient`（模型/纹理/配方/战利品）

## 七、搬运策略

1. 逐文件从源仓库复制（保持类名/包名），按第四节差异清单修 API；不要重命名以降低对照成本。
2. 每个系统走对应 skill：`port-content`（总流程）、`entity`、`curio`、`worldgen`、`datagen`、`capability`、`recipe-container`、`advancement-notes`、`shadow-difficulty`、`skill-system`、`client-rendering`。
3. 基础设施先于内容；低耦合内容先于 BOSS/维度。
4. 每搬一批跑一次 `runData`/`runClient`，避免错误累积。

## 八、风险与待定项

| 项 | 风险 | 处理 |
|----|------|------|
| NBT → DataComponents | 影响几乎所有容器/物品/网络包 | 优先 `CustomData` 过渡，再逐步强类型化 |
| 附魔数据驱动化 | 效果组件 API 差异大 | 单独任务重写 `Shelter`/`SwiftStrike` |
| Capability → Attachment | 同步语义不同 | `AttachmentType.sync` 或保留手写包 |
| GeckoLib 4.9 / Curios 9.5 / Patchouli 1.21 API | 细节需查文档 | 搬对应系统时用 MCP/源码核对 |
| Mixin 目标名 | mojmap 名称变化 | 用 `minecraft-dev` MCP 校验每个注入目标 |
| KubeJS 2101 | 插件 API 大改 | 最后处理，必要时降级为可选 |
| `GeckoLib.initialize()` | 可能已被移除 | Phase 1 验证，不需要则删 |
| 资源目录名 | 1.21 复数→单数 | 以 `runData` 输出为准 |
| 第三方 refmap | 映射渠道不同 | 优先用官方 NeoForge 版 jar；必要时修补 |
