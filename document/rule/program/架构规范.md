## 包名规范

- **反向域名**：`com.pasterdream.<modid>`
- **全部小写**，不含大写字母
- `modid` 必须与包名中的模组段一致，且满足正则 `[a-z][a-z0-9_]{1,63}`
- 当前 modid：`pasterdream`，包名：`com.pasterdream.pasterdreammod`

## 注册模式

### DeferredRegister 模式（NeoForge 标准）

所有注册对象使用 `DeferredRegister` + `DeferredHolder` 模式，在 `@Mod` 主类构造方法中统一注册到 Mod 事件总线。注册表引用 `Registries` / `NeoForgeRegistries` 常量，不再使用 `ForgeRegistries`：

```java
// 1. 在注册中心类中定义 DeferredRegister 和 DeferredHolder 常量
public class ModItems {
    public static final DeferredRegister.Items ITEMS = DeferredRegister.createItems(PasterDreamMod.MOD_ID);
    public static final DeferredItem<Item> EXAMPLE_ITEM =
            ITEMS.register("example_item", () -> new Item(new Item.Properties()));

    public static void register(IEventBus eventBus) {
        ITEMS.register(eventBus);
    }
}

// 2. 在 @Mod 主类构造方法中调用注册（构造参数由 FML 注入）
public PasterDreamMod(IEventBus modEventBus, ModContainer modContainer) {
    ModItems.register(modEventBus);
    ModBlocks.register(modEventBus);
    ModParticleTypes.register(modEventBus);
    ModCreativeModeTabs.register(modEventBus);
    modContainer.registerConfig(ModConfig.Type.COMMON, Config.SPEC);
}
```

> 游戏规则（`ModGameRules`）通过静态初始化调用 `GameRules.register()` 注册，不走 DeferredRegister。
>
> **数据驱动注册表**（1.21 起）：`Enchantment`（附魔）、`PaintingVariant`（画）不再是普通注册表，改用 `ResourceKey` + datagen 的 `RegistrySetBuilder`（详见「世界生成」小节），不走 `DeferredRegister`。
>
> 世界生成（`ConfiguredFeature`、`PlacedFeature`、`Biome`、`DimensionType`、`NoiseSettings`、`LevelStem`）同样通过数据生成器的 `RegistrySetBuilder` + `DatapackBuiltinEntriesProvider` 模式注册。

### 酿造

`ModPotions` 注册三种幸运药水，并在 `RegisterBrewingRecipesEvent` 中通过 `PotionBrewing.Builder#addMix` 注册配方。酿造台、梦之釜的 `VanillaBrewingAdapter` 和 JEI 酿造页都读取关卡的 `PotionBrewing`。

### 自定义附魔

`ModEnchantment` 定义六种附魔的注册键、适用物品、等级、费用和修补互斥关系。`ModWorldGenProvider` 调用其 `bootstrap` 生成附魔定义，`ModEnchantmentTagsProvider` 和 `ModItemTagsProvider` 分别生成获取方式与适用物品标签。疾风连击在附魔台适用于剑，斧通过铁砧附魔。其余五种为可交易、可从随机战利品获得的宝藏附魔。

疾风连击与聚梦使用 `ItemAttributeModifierEvent` 按物品和装备槽计算属性，修饰器以 `ResourceLocation` 标识。庇护和噬心诅咒通过 `EnchantmentDamageMixin` 在盾牌与无敌帧结算后、护甲减伤前处理，噬心诅咒先读取该阶段的伤害。

融梦修补与噬心修补通过服务端玩家刻末扫描背包、护甲、副手和 Curios 饰品，扣费经 Attachment 同步。融梦水晶护甲由其自身的修补处理器结算。`EnchantBookForEmeraldsMixin` 读取附魔书的存储附魔，使用 `ItemCost` 保留融梦修补的交易定价。混沌箭通过 `ArrowItem#isInfinite` 读取发射武器的噬心修补，发射时用 `INTANGIBLE_PROJECTILE` 标记控制免费箭的回收。

### 数据流

1. `RegistrySetBuilder` 中按顺序注册各 registry 的 bootstrap（注意依赖顺序：BIOME / DIMENSION_TYPE / NOISE_SETTINGS 在 LEVEL_STEM 之前）
2. `runData` 时 `ModWorldGenProvider` 按 builder 顺序调用各 `bootstrap(context)` 方法
3. `BootstapContext` 的 `register(key, value)` 产出 `data/{modid}/worldgen/` 下的 JSON 文件
4. 运行时通过 `ResourceKey` 引用（如 `ModTreeGrowers` → `ModConfiguredFeatures.DYEDREAM_TREE`）

风泊群岛地表结构阶段加载 `wind_journey_water_pool`。`WindJourneyWaterPoolFeature` 先调用 `DyedreamWaterPoolFeature` 生成湖泊，再按配置调用 `slumber_palm_tree`。树苗的 `TreeGrower` 使用同一个配置地物。水池扫描和树木放置在世界生成阶段只访问已完成地形生成的区块。

### 子包划分原则

- `worldgen/biome/` — 群系定义 + NeoForge Biome Modifier
- `worldgen/dimension/` — 维度类型 + 噪声设置 + LevelStem 注册
- `worldgen/` 根目录 — 地物（ConfiguredFeature + PlacedFeature）
- `worldgen/feature/` — 自定义 `Feature<?>` 实现类 + TreeDecorator，与注册入口类分离
- `worldgen/structures/` — 结构数据生成 Provider

### 维度/群系搬运流程

1. 维度类型 → `ModDimensionTypes.java`（`DimensionType` 构造，含 MonsterSettings）
2. 噪声设置 → `ModNoiseSettings.java`（`NoiseGeneratorSettings` 构造，含 NoiseRouter + SurfaceRules）
3. 维度注册 → `ModLevelStems.java`（`LevelStem` 构造，关联 BiomeSource + ChunkGenerator）
4. 群系注册 → `ModBiomes.java`（`Biome.BiomeBuilder` 构建，含特效、生物生成、雕刻器、特征列表）
5. 如需自定义 DimensionSpecialEffects → 使用客户端 Mixin（FogRendererMixin, LevelRendererMixin）注入

## 技能系统

瞬身术（Blink）基础链路已在批次 026 迁入，其架构链路如下：

```
ModKeyMappings (C 键) → BlinkPacket (C2S) → BlinkSkill (位移、冷却、回避效果)
                                                ↓
                               EvasionEffect + BlinkCooldownEffect
                                                ↓
                   PlayerEvents (回避伤害) → EvasionEffectHandler (成功回避特效)
```

### 各层职责

| 层 | 类 | 职责 |
|----|-----|------|
| 按键绑定 | `ModKeyMappings` | 注册 C 键，客户端检测按下 |
| 网络传输 | `network/skill/BlinkPacket` | 客户端→服务端无参数请求；服务端读取玩家当前状态与朝向 |
| 技能核心 | `world/skill/BlinkSkill` | 饱食度与冷却检查、位移计算、冷却设置、回避效果施加 |
| 特效处理 | `world/skill/EvasionEffectHandler` | 成功回避后的粒子、音效、冲刺与延迟尾迹 |
| 效果标记 | `effect/EvasionEffect` + `effect/BlinkCooldownEffect` | 瞬移后无敌帧 + 冷却计时 |

### 自定义属性

通过 `ModAttributes` 注册自定义属性，用于控制技能参数。可通过饰品或效果动态修正属性值：

| 属性 ID | 用途 |
|---------|------|
| `blink_cooldown_reduction` / `blink_consume` / `blink_range` | 瞬身术冷却缩减 / 消耗 / 范围 |
| `skill_cooldown_reduction` / `skill_damage_rate` | 战技冷却缩减 / 战技伤害 |
| `magic_damage_rate` | 魔法伤害倍率 |
| `san_variability` / `max_san_extra` | SAN 波动 / 上限 |
| `melt_dream_variability` / `max_melt_dream_energy_extra` | 融梦能量波动 / 上限 |
| `arrow_velocity` | 弹射物初速倍率 |

基础瞬身术使用 3 × `blink_consume` 的耗竭、50 tick 冷却（鞘翅 100 tick）和 6 tick 回避；创造模式跳过消耗与冷却。折翼天使雕像上弩已由 `BlinkSkill` 调用 `FracturedAngelStatueHandler` 接回：仅在 Curios 装备且主手持未装填弩时，使用 1.21 原版 `ProjectileWeaponItem.draw` 规则装填。回避衣装延长时长、转身衣装与反击饰品联动仍待迁入。
回避免伤在 NeoForge 的 `LivingIncomingDamageEvent` 中结算；该事件早于原版受击无敌判定，成功回避时需同时恢复 20 tick 无敌时间与 `lastHurt`，并在无敌时间内跳过本应由原版忽略的重复碰撞，以保持来源的贴身回避行为。

> 武器类技能（如萦风合金剑雷技能）不经过按键链路，直接在物品类中触发（如 `FluffyWindAlloySwordItem` → `WindAlloyLightningEntity`），详见「技能系统」相关的物品实现。

### 批次 027 的萦风装备链路

`FluffyWindBowItem` 在 1.21 `BowItem.createProjectile` 中读取融梦能量与引雷附魔，决定生成普通箭或 `FluffyWindArrowEntity`；后者保存弹药与引雷状态，由 `FluffyWindBowHandler` 在命中后追加落雷，并由 `FluffyWindArrowTrailRenderer` 在客户端绘制渐变三棱柱拖尾。`ModChannelingEnchantmentProvider` 生成原版引雷定义的适用标签，`ModItemTagsProvider` 将三叉戟标签和萦风弓加入该标签。

四件 `FluffyWindAlloyArmorItem` 的逐件属性由物品栈提供；`FluffyWindAlloyArmorHandler` 在服务端处理满套天气、伤害、投射物和缓降，`UsingItemSpeedMixin` 处理蓄力速度。客户端 `ModKeyMappings` 经 `WindHoverInputPacket` 上报空格输入；服务端仍核验装备与状态。`WindRunnerCloakItem` 与 `WindRunnerCloakHandler` 处理鞘翅飞行和撞墙保护，`CapeLayerMixin` 隐藏原版披风层。折翼天使雕像由 Curios 佩戴检查进入 `FracturedAngelStatueHandler`，并从 `BlinkSkill` 接入即时弩装填。

### 批次 051 的暗影合金弩与通用拖尾箭

`ShadowAlloyCrossbowItem` 在 1.21 `CrossbowItem` 基础上重写装填/发射：装填使用 `DataComponents.CHARGED_PROJECTILES`，发射前经 `MeltDreamEnergyHelper.getEffectiveConsumeCost` 扣除 0.2 融梦能量；触发被动时使用 `ShadowAlloyArrowEntity` 并写持久数据标记，`ShadowAlloyCrossbowHandler` 在 `ProjectileImpactEvent` 与 `LivingIncomingDamageEvent` 施加易伤和配置白名单负面效果。通用 `TrailArrowEntity` / `ArrowTrailRenderer` 负责弹药同步、光灵箭发光、客户端轨迹采样与三棱柱拖尾；`TrailArrowRenderer` 按弹药选择光灵箭/药水箭贴图。1.21 `AbstractArrow#setPierceLevel` 为 private，穿透等级经 `AbstractArrowAccessor` Mixin 写入；力量与无限附魔由物品类 `isPrimaryItemFor` / `supportsEnchantment` 放行。

## Mixin 注入

### 使用原则

模组使用 Mixin 进行必要的底层行为注入，分为通用与客户端专属两类。

| 分类 | 用途 |
|------|------|
| 通用（`mixins`） | 生物 AI、附魔与药水效果、营火、钓鱼、花盆、滑翔、结构模板、定位命令和工具系列共享行为 |
| 客户端（`client`） | 情景音乐、光照、方块模型、披风图层、雾效和界面渲染 |

纷争标记沿用原版发光状态的同步。生物在刻首清除死亡或已移除的目标，幻翼在设定目标时跳过带有染梦香水效果的玩家。动物吃草沿用原版 AI 与 NeoForge 生物破坏判定，染梦草方块被吃后变为染梦泥土。烟花通过 `@Shadow` 读取附身的实体，在双端保持超出巡航速度的前向动量。

睡眠跳时和命令天气写入主世界数据。灯影之下沿用主世界天气，并通过本维度的降雨插值同步客户端。结构方块存档和编辑数据包的尺寸范围为 0～127，偏移范围为 −128～127。编码前限制数值，以对齐原版有符号字节。流体冲刷保护沿用来源方块标签，由 `FlowingFluidMixin` 在判定流体是否可进入方块时读取。

亚伦柯斯双手将服务端的攻击目标状态同步到原版生物标记。战斗音乐统一由客户端的 `BossMusicHandler` 播放，双手共用一条音轨，脱战或战斗结束后淡出。战斗曲有效播放期间，`SelectMusicEvent` 停止原版背景音乐并暂停调度，淡出完成后原版恢复选曲。竞技场的 150 秒计时独立驱动增援波次。

### 配置文件

Mixin 配置文件位于 `src/main/resources/pasterdream.mixins.json`，声明所有 Mixin 类及目标环境（client/server）。

## 事件总线体系

NeoForge 仍有两级事件总线，但 `@EventBusSubscriber` 会自动按事件类型分流，无需指定 `bus`：

| 总线 | 获取方式 | 用途 | 示例 |
|------|---------|------|------|
| **Mod 总线** | 构造注入的 `IEventBus` | 注册、初始化 | `FMLCommonSetupEvent`、`RegisterPayloadHandlersEvent`、注册 DeferredRegister |
| **游戏总线** | `NeoForge.EVENT_BUS` | 游戏运行时事件 | `ServerStartingEvent`、`LivingHurtEvent` |

> 分流规则：事件实现 `net.neoforged.fml.event.IModBusEvent` → Mod 总线；否则 → `NeoForge.EVENT_BUS`。

### 事件订阅方式

1. **构造方法中注册**（适用于 `@Mod` 主类自己的方法）：
   ```java
   modEventBus.addListener(this::commonSetup);
   ```

2. **`@EventBusSubscriber` 注解**（适用于独立类的静态方法，自动分流）：
   ```java
   @EventBusSubscriber(modid = PasterDreamMod.MOD_ID)
   public class SomeHandler {
       @SubscribeEvent
       public static void onEvent(SomeEvent event) { ... }
   }
   ```

3. **显式注册到游戏总线**（适用于运行时事件）：
   ```java
   NeoForge.EVENT_BUS.register(this);
   NeoForge.EVENT_BUS.addListener(SomeHandler::onEvent);
   ```

## 网络系统（NeoForge Payload）

NeoForge 1.21.1 已移除 `SimpleChannel`，改为 `CustomPacketPayload` + `StreamCodec`：

```java
// payload 定义
public record SanSyncPacket(int value) implements CustomPacketPayload {
    public static final CustomPacketPayload.Type<SanSyncPacket> TYPE =
            new CustomPacketPayload.Type<>(ResourceLocation.fromNamespaceAndPath(MOD_ID, "san_sync"));
    public static final StreamCodec<RegistryFriendlyByteBuf, SanSyncPacket> STREAM_CODEC =
            StreamCodec.composite(ByteBufCodecs.VAR_INT, SanSyncPacket::value, SanSyncPacket::new);

    @Override
    public CustomPacketPayload.Type<? extends CustomPacketPayload> type() { return TYPE; }

    public void handle(IPayloadContext ctx) {
        ctx.enqueueWork(() -> { /* 主线程逻辑 */ });
    }
}

// 注册（Mod 总线）
@EventBusSubscriber(modid = MOD_ID)
public final class ModNetwork {
    @SubscribeEvent
    public static void register(RegisterPayloadHandlersEvent event) {
        PayloadRegistrar registrar = event.registrar("1");
        registrar.playToClient(SanSyncPacket.TYPE, SanSyncPacket.STREAM_CODEC, SanSyncPacket::handle);
        registrar.playToServer(BlinkPacket.TYPE, BlinkPacket.STREAM_CODEC, BlinkPacket::handle);
        // 双向：registrar.playBidirectional(...) / commonBidirectional(...)
    }
}

// 发送
PacketDistributor.sendToServer(payload);
PacketDistributor.sendToPlayer(serverPlayer, payload);
PacketDistributor.sendToAllPlayers(payload);
```

- 每个包一个功能，按子功能分子包（`san/`、`meltdreamenergy/`、`skill/`、`curio/`、`mortar/` 等），与源仓库一致。
- `registerMessage(id++, ...)` 的整型 id 机制不再存在，改由 `Type` 标识。

## 模组入口类结构

`@Mod` 主类的构造方法是唯一注册入口，按以下顺序组织：

1. 初始化第三方库（如 `GeckoLib.initialize()`）
2. 获取 Mod 事件总线
3. 注册各类 `DeferredRegister`（粒子 → 物品 → 方块 → 物品栏 → 实体 → ...）
4. 注册 Mod 总线监听器（`commonSetup`、`clientSetup`）
5. 注册游戏总线监听器（`NeoForge.EVENT_BUS.register`）
6. 注册配置文件

### 映射渠道

项目使用 mojmap（Mojang official）+ Parchment 参数名。NeoForge 官方开发产物均为 mojmap，Mixin 直接按 mojmap 名称解析。若个别第三方 jar 的 refmap 与当前映射不匹配（注入报 `No candidates were found`），优先改用其官方 NeoForge 版本，必要时修补 refmap。

### Curios 集成规范

- 饰品物品放在 `world/item/curio/` 包下，实现 `ICurioItem` 接口（约 57 个饰品类 + 5 个被动处理器：CurioPassiveHandler、SoulGemOfAkizukiAyaneHandler、MagnifyingGlassOfSherryHandler、SealOfTheCorruptedHandler、FracturedAngelStatueHandler）
- 当前已迁入饰品使用 Curios 9.5.1 内置的 `charm` / `head` 等槽位类型；`data/pasterdream/curios/entities/player.json` 将来源八类槽位分配给玩家，`curios/slots/ring.json` 将戒指槽设为 2 个。后续自定义类型再按锁定 API 实现，不能把规划中的 `init/ModCuriosSlots` 当作现有类
- 插槽物品标签 JSON 手动维护在 `src/main/resources/data/curios/tags/item/`；标签存在不代表玩家拥有对应槽位，批次 032 GameTest 同时验证玩家槽位分配与饰品属性修饰符
- 可使用 `SlotTypePreset` 预设来创建标准插槽类型，通过 `.size()` 指定插槽数量
- 跨物品的饰品被动按来源触发方式接入 `CurioPassiveHandler` 的 NeoForge 事件分支；饰品自身的持续效果通过 `ICurioItem.curioTick` 每 tick 处理。当前处理器只迁入蝴蝶星发卡的目标变更分支，其他分支依其直接引用逐批接入

### GeckoLib 集成规范

- 动画实体/方块使用 `GeoEntity` / `GeoBlockEntity` 接口
- 渲染器继承 `GeoEntityRenderer` / `GeoBlockEntityRenderer`
- 模型类继承 `GeoModel`，动画控制器继承 `AbstractAnimationController` 或使用 builtin 动画
- 几何模型文件（`.geo.json`）放在 `assets/pasterdream/geo/`
- 动画文件（`.animation.json`）放在 `assets/pasterdream/animations/`
- 显示设置放在 `assets/pasterdream/models/displaysettings/`
- 特殊模型（粒子/展示用）放在 `assets/pasterdream/models/custom/`

### 光影（Oculus/Iris）集成规范

- 兼容代码放在 `compat/shaders/` 包下，不硬依赖光影模组
- 全部通过反射访问 `net.irisshaders.iris.*`（`ShaderCompat` 检测是否加载/启用），仅当 `isShaderPackInUse()` 为 true 时才走特殊分支
- `ShaderBlockInjector` 负责向光影管线注入模组方块（如植物方块动效），`ShaderPackConfig` 读取光影包配置，`ShaderCompatEvents` 挂接客户端事件
- 服务端不可见：相关类标注 `@OnlyIn(Dist.CLIENT)`
- 与机械动力：汽鸣铁道等第三方 Mixin 存在冲突时，需在注入点做兼容判断

### JEI 集成规范

- JEI 兼容代码全部放在 `compat/jei/` 包下
- 使用 `@JeiPlugin` 注解注册插件
- 仅使用 JEI API（compileOnly 依赖确保不直接引用内部实现）
- 支持 11 种配方类型：claypan, dreamcauldron, dreamaccumulator, mortar, researchtable_copy, researchtable_research, brewing, shadowblastfurnace, weaponworkshopcraftingtable, dyedreamcontamination, fluidcontainerrelation
- 物品信息页集中在 `compat/jei/info/ModJEIInfoRegistry` 登记，在 `ModJEIPlugin.registerRecipes` 末尾统一调用，文案键为 `jei.pasterdream.<item>.info`；新增条目只改该处

### KubeJS 集成规范

- 兼容代码放在 `compat/kubejs/` 包下，继承 `KubeJSPlugin`（`PasterDreamKubeJSPlugin`）
- 通过 `registerBindings` 暴露绑定对象：`PasterDreamTips`（加载提示语）、`PasterDreamRarities`（品质）、`PasterDreamSkills`（技能冷却/伤害）、`PasterDreamFoods`（外部食物属性）
- `PasterDreamFoods.register(itemId, sanAdd, meltDreamEnergyAdd)` 可给任意物品（含原版/其他模组食物）附加 SAN 与融梦能量加成，进食时自动生效并同步、ToolTip 自动追加
- 食物注册实现位于 `compat/kubejs/food/`（`PasterDreamFoodRegistry` 注册表 + `PasterDreamFoodEvents` 事件）

### Patchouli 集成规范

- 指南书数据放在 `src/main/resources/data/pasterdream/patchouli_books/seniors_dream/`
- 资源文件放在 `src/main/resources/assets/pasterdream/patchouli_books/seniors_dream/`
- 支持中英双语内容（en_us + zh_cn）
- 当前支持 7 种配方类型：claypan, dreamcauldron, dreamaccumulator, mortar, researchtable_copy, researchtable_research, brewingrecipe
- 栏目：dyedream_world / foretold_dream / lamp_shadow_world / wind_journey / rules / story（含灯影之下结构文档：亚伦柯斯竞技场、暗影地牢、暗影熔炉等）

## 当前数据生成与验证链路

- `datagen/ModDataGenerator` 是唯一生成入口；服务端生成配方/配方解锁进度、战利品、标签和动态注册表，客户端生成模型/方块状态及语言。
- `ModWorldGenProvider` 的 `RegistrySetBuilder` 连接 `ModConfiguredFeatures`、`ModPlacedFeatures`、`worldgen/biome/ModBiomeModifiers`。其他 Provider 使用其完整 lookup，避免后续引用新动态注册项时缺失。
- 批次 091 的逐梦列车采用 `world/block/dreamtrain/` 的一格标记方块实体：仅服务端 ticker 检测邻近非旁观玩家，随后加载 `data/pasterdream/structure/dream_train.nbt` 放置整列列车并全服播报。`dream_train_marker.nbt` 是后续 jigsaw 结构入口；结构配置尚未迁入。对应染梦结构箱战利品由 `ModDyedreamStructureLootTablesProvider` 生成。
- 第一批只实现钛金基础内容所需 Provider，不以空 Provider 冒充其余系统已迁移。
- `tag/ModBlockTags`、`ModItemTags` 管理材料分类，跨模组标签使用 `c` 命名空间；挖掘等级与功能仍使用对应原版标签。物品标签用 `copy` 同步方块分类。
- `src/gameTest/` 独立源码集绑定同一 mod 的开发运行环境，发布 Jar 只含 main；测试场景资源亦不发布。GameTest 服务端使用 `build/run-gametest`，数据生成使用 `build/run-data`。
- CI 先 runData 并检查关键生成资源存在，再 build 与 runGameTestServer；`src/generated/` 不纳入版本控制，生成缓存不入包。

## 当前流体链路（批次 042、045、047、049、052、053）

- `ModFluids` 已注册融梦涌泉与熔融阴影的 `FluidType`、源液和流动液；`ModBlocks` 注册对应 `LiquidBlock`，`ModItems` 注册标准 `BucketItem`。两种桶使用 NeoForge 自带的物品流体能力，容量为 1000 mB；无需在 `ModFluidContainerRelation` 再登记桶映射。
- `world/fluidtype/PasterDreamBaseFluidType` 提供源贴图、流动贴图和染色客户端扩展；桶物品模型由 `ModItemModelsProvider` 的 `DynamicFluidContainerModelBuilder` 生成，流体标签由 `ModFluidTagsProvider` 生成。静态动画纹理保存在 `src/main/resources/assets/pasterdream/textures/block/`。
- 批次 045 迁入共享流体槽菜单/界面/网络同步、流体原料和通用配方匹配处理，研钵为首个消费者；配方失败时不修改输入。`FluidContainerRegistry`、`GenericContainerFluidHandler` 与 `ContainerBalanceHelper` 已有基础实现，组件保留配方及研钵工具配方已调用余料平衡。
- 批次 047 注册玻璃罐、水罐、牛奶罐、酵母罐、药引瓶、风植萃取液与墨水罐，补齐四种仅用于储罐/配方的存储流体；`ModFluidContainerRelation` 登记 6 条 125 mB 映射，`ModCapabilities` 为 7 个罐注册 `Capabilities.FluidHandler.ITEM`。水罐与牛奶罐走 `PasterDreamDrinkItem` 饮用并返还空罐，酵母与墨水配方接入 provider 级配平校验。
- 批次 049 注册玻璃杯及 6 种杯装饮品、6 种存储流体；容器关系增加 6 条 250 mB 映射，7 个杯装物品接入流体物品能力。填充杯通过 `craftRemainder` 返回空杯，`PasterDreamDrinkItem` 饮用时也按容器关系返还空杯；共享饮品类在 1.21 对瞬时效果服务端调用即时处理，持续效果仍走普通添加路径。
- 批次 052 注册空灵药瓶、融梦灵药瓶和狂暴战意灵药。空瓶的 1000 mB 容量由 `ModDataComponents.ELIXIR_BOTTLE_FLUID` 的 `SimpleFluidContent` 与 `ModCapabilities` 的 `FluidHandlerItemStack` 承载；`ElixirBottleItem` 根据 `ModFluidPropertiesRelation` 饮用、排液，客户端模型由 `ModItemModels` 包装并由 `ElixirBottleRenderer` 绘制液面。两种成品饮品沿用 `PasterDreamDrinkItem`，用 `craftRemainder` 返还空瓶。空瓶不登记到 `ModFluidContainerRelation`，避免与自身的流体能力叠加。炼药釜产物与狂暴战意灵药的生存获取仍待 T12-B；客户端视觉与多人同步待实机验收。
- 批次 053 注册通用 `potion` 流体与 `PotionFluidType`，药水效果存放在 FluidStack 的 `DataComponents.POTION_CONTENTS`，可随 `SimpleFluidContent` 持久化与网络同步；`helper/potionhelper/` 提供效果列表、名称、时长与加权颜色转换。`ModFluidPropertiesRelation` 登记 potion 每次 250 mB、32 tick 的饮用；`ElixirBottleItem` 展开效果 tooltip，创造栏生成各效果与全效果样例。`drinkSpecial` 在排液前执行，按饮用前余量折算效果。
- 批次 054 迁入 `world/block/dreamcauldron/` 的方块实体、菜单、界面、GeckoLib 渲染与独立药水处理模块；三罐容量为 2000/8000/1000 mB，配方保留有序物品/流体原料并通过通用处理器执行。`ModCapabilities` 对方块注册流体与物品接口，输出物品槽只允许提取；`ModNetwork` 承载合成和界面提示请求，方块实体更新包同步液罐、物品及动画状态。来源 `EffectList` 在配方解码时转入 `POTION_CONTENTS`，`ModJEIPlugin` 注册炼药类别、药水流体子类型与酿造模板。90 条来源配方已载入；另外 9 条待缺失前置物品迁入，客户端和多人行为待实机验收。
